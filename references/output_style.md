# 中文輸出文風指南

本檔定義忠實度、自然化、語氣與文章氣質。 當任務需要翻譯、重寫、修稿、review 中文段落，或判斷輸出是否像自然的臺灣繁體中文技術文章時，讀本檔。

不屬於本檔的內容：具體標點、空格、Markdown syntax、citation apparatus、link label、正式輸出檔污染邊界，以及可直接對應 linter surface signal 的局部句法規則。 這些規則放在 `references/output_grammar.md`。

## 0. 編輯優先序與忠實度邊界

### 0.1 忠實度與既有中文修稿

- 忠實翻譯優先於擴寫式說明
- 不可只為了讓中文聽起來完整，就自行補入原文未明示的步驟、因果、時間順序或背景知識
- smoothing 可以，invent 不行
- 修訂既有中文時，原句自然、正確且符合本輪要求，預設保留。 改動須對應具體的語法、語意、指涉或語氣問題，或使用者要求的改寫目的。 僅因可省略、改後較短或另一寫法也通順，不足以構成刪改理由
- 修稿的忠實度也涵蓋原句的人稱與領屬關係、體貌、情態及語氣。 判斷「我們」「了」「會」「一下」等成分的去留時，須核對它們在句中的作用

### 0.2 共現、時間關係與因果鏈

- 若 source 只是在表達共現、時間關係或關聯，不可無憑據把它改寫成新的流程順序或因果鏈
- 若 source 沒有明說施事者或操作主體，不要為了補齊中文句骨自行補出一個做事者
- 若 source 沒有明說結果或終點，不要為了讓句子有收束感而自行造一個結果補語

例：

- 避免：source 只說 `指令取回後`，中文擴寫成 `指令取回後會先解碼`，憑空補出下一步
- 優先：維持原句 `在取回指令後`，讓後續事件由 source 自己交代

### 0.3 Typo 與事實滑漏

- 若 source 含有明顯 typo 或事實滑漏，仍以忠實翻譯為主，並加上簡短譯者註，但不得在直接將正文改寫成「修正後的版本」
- 譯者註應明示這是譯者觀察，不是 source 原文

### 0.4 評價力度、保留詞與玩笑

- 不可把 source 的輕微評價、保留詞或玩笑，升級成更強的稱讚、命令、舞台化語氣或 sales pitch
- 對 `good`、`nice`、`interesting`、`early`、`perhaps`、`maybe`、`we think`、`we wonder` 這類詞，中文應保留原本力度
- 若 source 只是平實介紹某書或論文在談什麼，中文也應優先維持平實介紹，不要自行補成 `強烈推薦`、`快去讀`、`之後你會感謝我們` 之類的讀者指令
- 若笑點高度依賴英語語境、文化梗或作者口條，中文直譯會顯得做作時，可縮成較平實的忠告。 不要為了保留笑點而自行加戲

例：

- 避免：`一本絕佳的計算機結構書。 去讀`
- 優先：`一本有關計算機結構的好書`
- 避免：`這篇論文非常精彩，強烈推薦`
- 優先：`這篇論文很有意思`
- 避免：`別越過 GO，更重要的是，不要領那 200 元你很需要的遊戲幣`
- 優先：`在沒有先對硬碟有一定程度的了解前就讀 FFS，實在沒什麼道理`

## 1. 中文自然化與文章氣質

- 自然且精確的中文技術段落，優先於僵硬的說明書腔
- 文法正確不等於文氣正確。 若句子沒有錯字、沒有明顯語病，但讀起來像模板、像宣傳、像 AI 總結，仍要重寫
- 若翻完後仍看得出明顯英文句骨，應直接重寫句子，而不是只補 glue word
- 優先讓動詞推動句子，而不是讓抽象名詞撐住子句骨架
- 翻譯時，兩種寫法都合文法且忠實，通常取較自然的一種。 修訂既有中文時，依 0.1 判斷是否需要改動，不以較短的版本作為預設
- 若英文把事件包進 nominalization、`preposition + V-ing` 或高密度名詞塊，中文通常應還原成事件子句。 具體句法規則看 `references/output_grammar.md`
- 若中文已自然，不要為了顯得完整而補一層解說，例如 `這代表...`、`換句話說...`、`這也意味著...`。 補充內容的來源與任務依據另依第 3 節核對

例：

- 避免：`一種常見方法`
- 優先：直接說清楚是哪個方法、做什麼用
- 避免：`這也意味著...`
- 優先：直接寫出實際結果或推論

## 2. 語域與語氣

- 盡量貼近原文的語域
- 若 source 明顯正式，譯文也應維持正式
- 若 source 明顯較口語，譯文可自然，但不可滑進原文沒有授權的俚語感
- 若 source 的段落只是平實說明，中文也應維持平實，不要補成宣傳文案或讀者命令
- 若 source 在某個位置保留不確定、推測、玩笑或輕微評價，中文也要保留同等力度

## 3. AI 腔與解說具體性

撰寫文章、提案、計畫、進度更新與完成回覆時，圍繞本輪目的交代事實、動作、結果、下一步行動及實際限制

- 對自行追加的澄清、排除、保證、不必做某事的補充與範圍說明，逐句確認它回答了使用者哪個問題，或提供了哪項理解、操作及決策所需的資訊。 刪除後仍能完整回答問題、交代結果及必要限制的補充內容，應刪除該項補充。 同句中的必要資訊繼續保留
- 這項檢查以資訊為單位，包含句內附註、獨立句、跨句及跨段內容。 `不是 A，而是 B`、`A。不會 B`、`不需要另看其他文件`、`不要求各建一個 class` 與 `原有修改沒有被覆寫` 都須核對任務用途。 改成肯定句、換詞或拆句，仍須檢查同一項補充資訊
- 遇到 `只`、`才`、`僅` 等限定語，核對限定的對象、條件或結果，以及這項限定對本輪任務的用途。 刪除無任務用途的補充，直接寫出需要的資訊、判準及動作
- 翻譯來源明示的對比、否定或澄清時，忠實保留其資訊與力度。 回答使用者已提出的具體疑問、誤解或比較要求時，回應對應內容。 回報實際故障、未完成驗證或使用者明示要保留並確認的項目時，交代查驗結果。 保留這些內容須能指出來源位置、使用者的具體要求或實際工作紀錄
- 內容可能正確、來自自己較早寫的筆記，或能預防自行假設的「常見誤解」，都不足以構成新增補充的理由。 直接陳述有依據且完成任務所需的資訊。 需要保留的重點資訊，直接寫成主句
- `所謂...就是...` 用於來源確實在定義的術語。 `這也意味著...` 用於來源支持的推論關係。 介紹檔案、工具或流程時，說明它的用途與行為。 陳述下一個事實時，承接該事實
- 文章與章節開頭依 [style 4.1](#41-文章目的背景與前提) 建立對象、問題及新主題的用途，再安排必要的導覽
- explanation-oriented writing 不可只列抽象類別名稱，必須交代具體檔案、具體責任、具體行為
- 若用了 workspace 內部術語，首次出現時要用白話展開
- 長句可以更精確，但長句應補足條件、動作、結果與因果，不要只把內部控制詞串成一串名詞
- 對 repo guide、workspace README、code report、workflow explanation、system overview 與風格檢查摘要，描述某個 layer、folder、file family 或 rule family 時，至少補出下列其中兩種具體資訊：裡面放了什麼、它控制什麼實際決策、agent 或使用者在什麼時候會讀它、它和相鄰層有何差異、一個代表性檔案或例子
- 若段落只說 `提升品質`、`確保一致性`、`建立清楚邊界`，但沒有交代具體對象、行為或判準，視為太抽象，改寫成可驗證的檔案、步驟、條件或結果
- 不要自行補 source 沒有明說的施事者、因果鏈、時間順序或結果補語來讓說明看起來完整。 這類忠實度邊界仍以本檔第 0 節為準
- 教學式說明先依 4.1 建立理解所需的背景與問題，再介紹核心規則、進階條件與例外。 各項資訊在讀者需要它的位置展開
- 若要把理論規則轉成學習者版說明，輸出應包含可操作判準、必要例句、常見錯誤與延伸條件，但不要把理論標籤當成讀者必懂的前提
- Binding、topic、DP、VP 這類語法概念若出現在教學式輸出中，先用普通中文說明要檢查的關係，再補英文術語。 一般翻譯輸出不主動展示這些術語

例：

- 避免：`這裡主要處理術語邊界`
- 優先：`這裡主要決定哪些詞保留英文、哪些詞翻成中文，以及章節內第一次出現的詞要不要先做雙語介紹`
- 避免：`這段主要在處理 output contract`
- 優先：`這段主要在說明這次最後要交付的是完整譯文、review 報告，還是其他特殊形式的輸出`

## 4. 段落節奏與 Markdown prose

- 每段優先控制在 2-5 行，高密度段落通常應低於約 150 個中文字
- 短段落政策不等於 sentence-per-line 的硬斷行
- 正式輸出以乾淨 Markdown 為主
- 不要求段落和 source 1:1 對應。 只要資訊忠實，必要時可重分段
- 對多個平行短項目，例如 loops、blocks、fields、units，可以使用 bullet
- 規格步驟敘述優先保留編號、縮短句尾、把動詞往前提
- 段落內包多層邏輯時主動重分段，而不是用分號硬串
- 若為了解說完整而把背景、條件、例外與結果全塞進單段，優先拆成「先判斷什麼」「怎麼改」「例外是什麼」三段或清單
- 若 source 是平實段落，譯文不要每段都補總結句。 過度總結會讓文字顯得像 AI 產出的教材摘要

### 4.1 文章目的、背景與前提

文章或章節開頭，從讀者已知的內容建立講述對象與目前需要解決的問題。 續章可以承接前文已得到的結果，獨立文章可以從讀者熟悉的使用情境或需求切入，再說明接下來介紹的概念、方法或模型能幫助我們理解什麼。 所需背景取自來源、已接受的前文與已確認的任務資料，新增事實仍依第 0 節核對忠實度

需要閱讀導覽時，將它放在讀者已理解主題用途的位置，讓各項內容的次序對應問題如何逐步得到解答。 寫出「先理解 A，才能理解 B」前，讀者應已知道 B 是什麼、為什麼需要理解 B，以及 A 如何提供所需的前提。 「先、再、最後」用來表達已有依據的時間、條件或解說次序，各步之間的承接仍須由對象、動作與目的交代

開頭須讓讀者取得理解後文的根據。 具體事件、方法名稱、圖名、映像檔與命令，在介紹用途後引入。 審閱「先看一個事件。」「本章先……」等開頭時，確認它們之前或所在段落已建立對象與問題。 首句很短並立即收句時，優先檢查它提供了哪些背景、下一句承接了什麼。 調整句長或標點後，重新核對首句的內容與前後承接

前文已交代本節問題時，承接已知內容展開。 使用者要求操作步驟，或來源本身就是操作說明時，可依該任務直接交代動作。 分段與導覽的篇幅隨任務安排，必要的術語與前提放在使用它們的位置之前

每段決定一個核心問題，逐句提供回答這個問題所需的資訊。 下一段可以處理前段留下的問題、延續同一對象，或以已得到的結果引出新內容。 轉換主題時交代它與目前問題的關係。 重述導覽或結論時，核對這一段增加了哪項讀者需要的資訊

例如，介紹座標轉換時，開頭從幾何資料會經過哪些操作，推進到組合操作的困難，再引入表示方法：

```text
幾何資料在不同座標系統之間移動時，會反覆經過縮放、旋轉與平移。 如果每一種操作都採用不同的表示方式，會使我們難以組合轉換順序，也不容易算出返回原座標系統的操作。 齊次座標會替位置增加一個分量，讓我們能把這些轉換都寫成矩陣乘法。 後續只要沿著矩陣的乘法順序，就能追蹤一個點轉換的過程了
```

第一句建立座標轉換的操作背景，第二句指出表示方式不同會帶來什麼困難。 後兩句介紹了齊次座標如何協助組合轉換，以及讀者如何利用這項表示追蹤一個點的轉換過程。 每句都使用前句已交代的資訊，讓新概念在讀者需要它的位置出現

重新閱讀文章及各章節開頭時，指出讀者從哪項已知內容開始、對象與問題在哪裡成立、新主題提供什麼幫助，以及導覽如何承接這些資訊。 前文已建立的內容可作為根據。 缺少的技術前提或因果另記待查證事項

### 4.2 句首承接、段落主線與語態

句子開頭為讀者建立本句講述的對象或背景，這部分稱為主題位置。 用能銜接前文的對象、結果、問題或條件開展下一句，讓讀者知道本句沿著哪項已知資訊繼續。 時間或條件框架也可以提供這個起點，中文句骨依 grammar 2.3 選擇

段落可以持續沿同一對象增加條件、動作與結果，也可以讓前句重要的新資訊成為下句的已知背景。 每次轉換核對前後的對象與根據。 [寫回的例段](#44-例子與推導融入正文)從既有值、操作結果與遮罩的設定開始，逐步說明如何取出位元並組合成新值

沿做事者說明時，從做事者及其動作展開。 受事是本句要強調或段落持續追蹤的對象時，可以讓它留在句首，再交代施事與動作。 被動表述的保留條件依 [grammar 2.6](output_grammar.md#26-把--被--受)，保留時須指出前後文或文章問題的依據。 例如，同一個事實可以接入兩種前文：

- 我們要看蜜蜂在傳播過程中做了什麼：「蜜蜂傳播花粉」
- 花粉如何傳到別處：「花粉由蜜蜂傳播」

第一個例句沿蜜蜂的行為展開，第二個例句沿花粉的傳播展開，兩者保存同一個事實。 第二個例句中的花粉是已明示的問題對象，因此符合受事為重點的條件。 具體句法依 grammar 2.3 與 2.6。 來源未交代施事者時，保存資訊缺口。 主詞已由緊鄰上下文清楚承接時，保留自然省略。 切換主體或有多個候選時，明示有來源依據的主詞

重新閱讀時，說出每句從前文承接了什麼、增加了什麼，以及下句如何用到它。 只有連接語而缺少對象與根據的銜接，需回到來源補查。 事件的條件、時間、轉折與因果依 grammar 2.8 表達

### 4.3 主詞、動作與收束處的重點

提出主體後，盡快交代它的主要動作或狀態。 主詞與動詞之間的長插入說明，依資訊角色安排到背景句、前置框架或獨立句。 必要的長定語保留完整關係，句長與詞數只供找出值得重新檢查的位置

用適當動詞表達真實動作，核對誰讀取、比較、選擇或寫回了哪項資料。 定義、分類與狀態也可依 grammar 保留自然述語。 完成事件、新狀態與慣常行為依 grammar 2.5 判斷「了」的位置，例如「這個介面現在穩定了」交代已成立的新狀態，慣常啟動程序則沿該節的無標記或「會」表述

值得讀者記住的重要新資訊，放在子句、句子或段落的完整收束處。 這個位置稱為強調位置，可以涵蓋整個述語、結果或已引介的列表。 句末體貌詞隨所屬述語保留，標點依 grammar 選擇

[寫回例段](#44-例子與推導融入正文)以保留高位元、更新低位元的計算收束到 `0xA5`。 若後面還要交代參數清單或背景，依其用途另作安排，讓本段重要的計算結果有清楚位置。 多項同等重要的結果各自形成可辨認的完整子句、句子或列點

重新閱讀時，核對主詞提出後何時才出現主句動作、實際作用關係是否由動詞交代，以及讀者在收束時記住的內容是否就是本段重點。 長插入、句末附註與多項結果一併依上下文判斷

### 4.4 例子與推導融入正文

例子放在讀者需要它理解操作或推論的位置。 引入例子時交代必要設定，計算或操作各步都對應正在解釋的規則，結果接回正文要回答的問題。 例如，下面說明 stencil write mask 如何保留既有值中的位元，並採用操作結果中的位元：

```
Stencil write mask 會逐 bit 選擇 stencil attachment 是要保留既有值，還是採用 stencil operation 算出的新值。 假設目前具有下列資料與設定：

- 既有 stencil 值：$S_{\mathrm{old}}=\mathrm{0xA2}$
- Stencil operation result：$S_{\mathrm{operation}}=\mathrm{0x35}$
- Application 設定的 stencil write mask：`glStencilMask(0x0F)`，所以 $M=\mathrm{0x0F}$

將三筆 8-bit 資料展開後，可以得到：

$$
\begin{aligned}
S_{\mathrm{old}}
&=\mathrm{0xA2}=1010\,0010,\\
S_{\mathrm{operation}}
&=\mathrm{0x35}=0011\,0101,\\
M
&=\mathrm{0x0F}=0000\,1111.
\end{aligned}
$$

Write mask 中的每個 bit 都會決定結果中同一個 bit 的來源：

- Mask bit 為 $0$：沿用 $S_{\mathrm{old}}$ 中對應的 bit
- Mask bit 為 $1$：採用 $S_{\mathrm{operation}}$ 中對應的 bit

由於 `0x0F` 的高四個 bits 都是 $0$，低四個 bits 都是 $1$。 因此新值會保留 $S_{\mathrm{old}}$ 的高四個 bits，並採用 $S_{\mathrm{operation}}$ 的低四個 bits

在 8-bit 範圍內，將 `0x0F` 的每個 bit 逐一取反，就會從 $0000\,1111$ 得到 $1111\,0000$，也就是 `0xF0`。 管線會先使用 `0xF0` 取出既有值中需要保留的高四個 bits：

$$
\mathrm{0xA2}\mathbin{\&}\mathrm{0xF0}
=\mathrm{0xA0}.
$$

接著使用 write mask `0x0F` 取出 operation result 中允許寫入的低四個 bits：

$$
\mathrm{0x35}\mathbin{\&}\mathrm{0x0F}
=\mathrm{0x05}.
$$

最後再對兩部分執行逐位元 `OR`，組成準備交給 framebuffer write 的 stencil 值：

$$
\begin{aligned}
S_{\mathrm{new}}
&=\mathrm{0xA0}\mathbin{|}\mathrm{0x05}\\
&=1010\,0000\mathbin{|}0000\,0101\\
&=1010\,0101\\
&=\mathrm{0xA5}.
\end{aligned}
$$

因此，新值的高四個 bits 來自既有 stencil 值 `0xA2`，低四個 bits 則來自 operation result `0x35`。 Stencil write mask 最後交出的結果是 `0xA5`，framebuffer write 會使用這筆結果來更新 stencil attachment
```

例子在計算前交代了既有值、操作結果與遮罩，再分別取出需要保留與寫入的位元。 兩部分組合成 `0xA5` 後，最後一段接回模板附件的更新，讓計算結果回到正文所說明的操作

重新閱讀例子時，核對讀者能否從已交代的設定走到每個中間結果，以及結果如何支持正文。 來源缺少前提或中間根據時，記錄待查證資訊。 新增背景、施事、因果及結果依第 0 節核對忠實度
