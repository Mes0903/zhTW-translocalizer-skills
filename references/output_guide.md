# 中文輸出指南

本檔定義此 workspace 的中文輸出規則。 執行任務時，直接依本檔判斷用詞、句法、標點、Markdown 與 citation 的處理方式

## 0. 編輯優先序與忠實度邊界

### 0.1 忠實翻譯優先

- 忠實翻譯優先於擴寫式說明
- 不可只為了讓中文聽起來完整，就自行補入原文未明示的步驟、因果、時間順序或背景知識
- smoothing 可以，invent 不行

### 0.2 共現、時間關係與因果鏈

- 若 source 只是在表達共現、時間關係或關聯，不可無憑據把它改寫成新的流程順序或因果鏈
- 若 source 沒有明說施事者或操作主體，不要為了補齊中文句骨自行補出一個做事者
- 若 source 沒有明說結果或終點，不要為了讓句子有收束感而自行造一個結果補語

例：

- 避免：source 只說 `指令取回後`，中文擴寫成 `指令取回後會先解碼`，憑空補出下一步
- 優先：維持原句 `在取回指令後`，讓後續事件由 source 自己交代

### 0.3 Typo 與事實滑漏

- 若 source 含有明顯 typo 或事實滑漏，仍以忠實翻譯為主，並加上簡短譯者註，但不得在直接將正文改寫成「修正後的版本」
- 譯者註應明示這是譯者觀察，不是 source 原文

### 0.4 評價力度、保留詞與玩笑

- 不可把 source 的輕微評價、保留詞或玩笑，升級成更強的稱讚、命令、舞台化語氣或 sales pitch
- 對 `good`、`nice`、`interesting`、`early`、`perhaps`、`maybe`、`we think`、`we wonder` 這類詞，中文應保留原本力度
- 若 source 只是平實介紹某書或論文在談什麼，中文也應優先維持平實介紹，不要自行補成 `強烈推薦`、`快去讀`、`之後你會感謝我們` 之類的讀者指令
- 若笑點高度依賴英語語境、文化梗或作者口條，中文直譯會顯得做作時，可縮成較平實的忠告。 不要為了保留笑點而自行加戲

例：

- 避免：`一本絕佳的計算機結構書。 去讀`
- 優先：`一本有關計算機結構的好書`
- 避免：`這篇論文非常精彩，強烈推薦`
- 優先：`這篇論文很有意思`
- 避免：`別越過 GO，更重要的是，不要領那 200 元你很需要的遊戲幣`
- 優先：`在沒有先對硬碟有一定程度的了解前就讀 FFS，實在沒什麼道理`

## 1. 術語與雙語格式

### 1.1 術語類型與預設處理

先把反覆出現的詞分成三類：

- true name / label / token
  - 例如 code identifier、path、CLI flag、macro、register 名稱、figure label
  - 預設保留英文
- section-defined term
  - 章節內會反覆出現、需要先定義再固定形式的詞
  - 預設首次使用 `中文（English）`
- general concept
  - 一般技術概念詞
  - 預設翻成中文，必要時參照 `references/glossary.md` 與 `references/preferred_taiwan_terms.md`

常見 general concept 的預設：

- `architecture` -> `架構`
- `microarchitecture` -> `微架構`
- `multithreading` -> `多執行緒`
- `approximation` -> `近似` / `近似值`

例：

- 避免：`在這個 architecture 中`
- 優先：`在這個架構中`

`X is a ... that ...` 類型的定義句，優先譯成 `X 是...，用來 / 負責...`：

- 例如：`Exception is a CPU feature that allows ...` -> `例外是 CPU 提供的功能，讓...`

### 1.2 英文保留邊界

下列情況通常保留英文：

- code identifier、path、URL、email、macro、enum、constant
- ISA / register / instruction 名稱
- true name / label / token
- 翻成中文會顯得笨重或失去辨識度的縮寫密集術語
- 架構圖中的 unit / block label，若它們扮演實際物件名稱
- architecture 文字中的專名 block / loop / unit：保留 English name，必要時補一句中文功能說明

不要只為了視覺一致，就強迫每個技術詞都翻成中文

另一方面，專業領域中的一般概念詞預設翻中文，不要因為專業語境就自動保留英文

正式名稱（proper name）與外部查證：

- 對電影名稱、書名、地名、人名等正式名稱，若有官方臺灣譯法，優先採用它
- 公司名稱、主要產品名稱與常見平台名稱通常維持其通行形式，除非 task 另有要求
- 若沒有官方譯名，但仍需要翻譯，可在首次出現時於括號內補原名

例：

- 可保留：`SIMD`、`CUDA`、`PTX`
- 可保留：`off-chip` 記憶體存取
- 避免：直接把一般概念詞寫成英文
- 優先：`直接證明（Direct Proof）`

### 1.3 章節級高頻概念的一致性

- 若某個 general concept 會在整章高頻重複，優先先決定中文主形式
- 首次可用 `中文（English）`，後續以中文為主，不要在同章內中英來回搖擺
- 專名、token 與 API 名稱保留英文。 但一般概念詞不要因為專業語境就偷懶留英文
- 同一詞根的名詞、動作與慣用術語不必硬譯成完全同一字面，重點是中文自然且章節內穩定

例：

- 避免：`介紹一種叫做 lock 的東西。 thread 會進入 critical section`
- 優先：`介紹一種叫做鎖（lock）的東西。 執行緒會進入臨界區`
- 優先：`並行（concurrency）`、`執行緒（thread）`、`鎖（lock）`、`臨界區（critical section）`
- 可接受：`spinlock` -> `自旋鎖`； `spinning` -> `忙等`

### 1.4 首次雙語與後續固定形式

- 高影響力的 section-defined term，首次出現採 `中文（English）`
- 中文上下文中的一般雙語術語，不採 `English（中文）`
- 首次定義後，後文固定單一形式，不可在 English-only 與 Chinese-only 之間隨機漂移
- 若是 true name / label / token，本體可保留英文主形，不必硬做雙語括號
- 短而常見的 section-defined term 不要長期保留英文，優先首次雙語後固定中文

例：

- 範例：`Exception handler`
- 優先：`例外處理器（Exception handler）`
- 避免：`Exception handler（例外處理器）`
- 避免：章節內反覆使用 `Exception handler` 卻從未給中文定義

### 1.5 縮寫、label、true name 與 token

- `SIMD`、`SIMT`、`CUDA`、`PTX`、`SFU` 這類縮寫密集術語，若完整中文展開不自然，優先保留縮寫
- 首次出現時可補一個簡短的中文提示，但不要每次都機械式地做雙語展開
- block label、unit label、圖中標記若主要作用是辨識物件，不要把它們寫成一般概念詞
- `is called / labeled / referred to as` 類結構，依語境選 `稱為`、`記為`、`在圖中標成`
- 避免：機械式地寫 `被稱作`

## 2. 中文句法與自然化

### 2.1 整體寫法指引

- 自然且精確的中文技術段落，優先於僵硬的說明書腔
- 若翻完後仍看得出明顯英文句骨，應直接重寫句子，而不是只補 glue word
- 優先讓動詞推動句子，而不是讓抽象名詞撐住子句骨架
- 詞類判斷先看中文實際分布、搭配與成分關係，不要機械式地照英文詞類標籤映射
- 若某個選詞會連動 `很`、`對`、賓語、補語或量詞搭配，就以中文實際分布為準，不要硬追來源的名詞 / 動詞 / 形容詞標籤
- 若某個中文組合其實可拆、可擴充，或更像句法短語，不要為了追求「像術語」而硬縮成固定詞
- 修飾範圍與成分群組要依中文自然成分來決定。 若沿 source 線性順序會切錯，就直接重排
- 避免：保留形容詞形式卻直接接裸賓語，或保留名詞形式卻硬塞動詞論元
- 優先：讓詞類選擇和後續賓語 / 補語配置一起成立
- 避免：把可拆組合機械式地壓成難懂的緊縮名詞
- 優先：保留自然的修飾 / 支配 / 補語關係，必要時允許插入或展開成分

例：

- 避免：`一種常見方法`
- 優先：直接說清楚是哪個方法、做什麼用
- 範例：`We divide our discussion into two parts` -> `我們會分兩部分來討論`
- 範例：`hardware protection mechanisms` -> `CPU 提供的硬體保護機制`
- 避免：`這也意味著...`
- 優先：直接寫出實際結果或推論

一些推薦的寫法：

- `is used to ...` -> `用來...` / `可用於...`
- `is designed to ...` -> `設計成...` / `目的是...`
- `is called ...` -> `稱為...`
- `called / labeled / referred to as ...` -> 依語境選 `稱為` / `記為` / `在圖中標成`
- `can be ...` -> `可以...` / `可能...`，或直接改成有限動詞
- `In the literature, ...` -> `文獻中...`
- `During execution, ...` -> `在執行時...`
- `At this stage, ...` -> `在這個階段...`
- `It is important that ...` -> `...很重要` / `必須...`
- `The key difference is ...` -> `主要差別在於...`
- `X provides Y` -> `X 提供 Y` / `X 讓 ... 能 ...`
- `We'll / We will ...` -> `我們會...` / `我們接下來會...`
- `We divide our discussion into two parts` -> `我們會分兩部分來討論`

若兩種寫法都合文法，通常取讀起來比較自然的那一種，不要硬挑「更接近原句骨」的形式

修飾範圍與成分群組要依中文自然成分重新決定：

- 避免：`舊插件和腳本`（若其實要表達兩組都受「舊」修飾）
- 優先：`舊插件和舊腳本`
- 避免：把 `關於快取一致性的說明文件` 錯切成 `關於快取` + `一致性`
- 優先：`關於快取一致性的說明文件`

### 2.2 事件表述與名詞化還原

- 若英文把事件包進 nominalization、`preposition + V-ing` 或高密度名詞塊，中文預設還原成事件子句
- `名詞組 + 的 + 動詞組` 只在資訊壓縮真的有價值時才用
- 若只是把自然事件句塞成書面名詞塊，應還原
- 使用這種結構前，先確認前面的名詞組比較像做事者、受影響者，還是單純的參照點。 角色不清楚時，不要硬寫
- 常見修法：
  - `在...時`
  - `...的同時`
  - `...之後`
  - `先...再...`
  - 直接有限動詞子句

例：

- 避免：`來源運算元的取回`
- 優先：`在取回來源運算元時`
- 範例：`in parallel with fetching source operands` -> `在取出來源運算元的同時`
- 避免：`遮罩的決定`
- 優先：`決定遮罩值`

### 2.3 主題、語態與資訊結構

- 若英文被動句不需要把受事者推到前景，優先用主動或 frame-first 中文，而不是機械式地改成 `被`
- 中文通常適合 `frame -> proposition`，例如：
  - `文獻中...`
  - `在執行時...`
  - `在這個階段...`
- 若相鄰子句共用同一主題，且不會歧義，不要機械式地重複主語
- 焦點型 `是` 只在真的要回答「到底是誰 / 哪一個 / 何時」時使用，不要把它當成泛用強調字
- `有` 至少要分清楚領屬、存在與 `有 + V` 體貌用法，不可混成單一的「有」

前置成分只有在真的建立話題時才保留：

- 避免：`三個測試案例，系統在初始化時會先執行`
- 優先：`系統在初始化時，會先執行三個測試案例`

數量短語若焦點不在數量本身，不宜直接放句首：

- 避免：`三個 worker，會在這一輪被建立`
- 優先：`這一輪會建立三個 worker`

連續子句共用主題時省掉重複主語：

- 避免：`系統會先收集事件，系統接著會更新狀態，系統最後會通知使用者`
- 優先：`系統會先收集事件，接著更新狀態，最後再通知使用者`

`是` 與 `有` 的基本差異：

- 等同 / 類屬判斷用 `是`，引入存在或領屬用 `有`
- 避免：`執行期系統是 retry queue`
- 優先：`執行期系統裡有一個 retry queue`
- 避免：`這個 queue 有 retry buffer`
- 優先：`這個 queue 是 retry buffer`

普通判斷句不是可逆等號句，先判斷是類屬、辨識還是部分與整體：

- 避免：`快取層就是保護機制`
- 優先：`快取層是保護機制的一部分`
- 避免：`重試佇列就是背景工作管理機制`
- 優先：`重試佇列是一種背景工作管理機制`

一般敘述不要用 `是...的` 或 `...的是...` 製造強調：

- 避免：`這個流程是會在初始化階段執行的`
- 優先：`這個流程會在初始化階段執行`
- 避免：`系統使用的是 hash table 來快取結果`
- 優先：`系統用 hash table 快取結果`

焦點型 `是` 不應插進謂語骨架中段：

- 避免：`系統把結果是寫回記憶體`
- 優先：`系統把結果寫回記憶體`
- 避免：`這個欄位被是初始化的`
- 優先：`這個欄位是在初始化階段建立的`

`有 + V` 不是一般書面段落的完成標記：

- 避免：`系統有完成初始化`
- 優先：`系統已完成初始化`
- 避免：`這個模組有支援快取寫回`
- 優先：`這個模組支援快取寫回`

存在句的 `有` 預設引入無定名詞，後面若是定指，改成處所句或領屬句：

- 避免：`記憶體裡有那個暫存區`
- 優先：`那個暫存區在記憶體裡`
- 避免：`這個結構裡有該索引表`
- 優先：`這個結構裡有一個索引表`

`會 / 可能 / 應該` 與 `敢 / 肯 / 願意` 不是同一類情態詞：

- 避免：`這個錯誤願意在高負載下發生`
- 優先：`這個錯誤可能在高負載下發生`
- 避免：`這個欄位肯在初始化後出現`
- 優先：`這個欄位會在初始化後出現`

例：

- 範例：`在文獻中被提出` -> `文獻中也有提出過...`
- 避免：`而跨 lane 的 predicate 測試也曾在文獻中被提出`
- 優先：`文獻中也有提出過跨 lane 的 predicate 測試方案`
- 範例：`trap is handled by kernel` -> `kernel 會處理 trap`
- 避免：`trap 被 kernel 處理`
- 優先：`kernel 會處理 trap`

### 2.4 `的 / 地 / 得`

- 把 `的 / 地 / 得` 視為結構標記，不是裝飾
- 若省略它們會讓修飾、補語或成分關係模糊，就不要硬省
- `的`
  - 名詞性修飾與結構連接
- `地`
  - 狀語標記
- `得`
  - 補語標記
- 不要把這三者混用，也不要只靠語感亂填

定語修飾名詞、讀起來生硬時補 `的`：

- `一種常見方法` -> `一種常見的方法`
- `複雜控制流程` -> `複雜的控制流程`
- `跨 lane predicate 測試` -> `跨 lane 的 predicate 測試`

狀語修飾動詞、省略後會削弱修飾關係時補 `地`：

- `有系統整理` -> `有系統地整理`
- `清楚說明` -> `清楚地說明`
- `系統性比較` -> `系統性地比較`

補語關係用 `得`：

- `看得出來`
- `整理得更清楚`
- `保留得很好`

卡在名詞片語 calque 時，優先改成自然片語，並補上必要功能詞或時間框架：

- `一種常見方法` -> `一種常見的方法`
- `指令取回後` -> `在取回指令後`

### 2.5 `了`

- 先區分：
  - 動詞後的 `了`：已完成 / 帶結果事件
  - 句尾的 `了`：新狀態成立、discourse update 或即將發生的變化
- 不要只因英文是 past tense 就補 `了`
- 一般事實、慣常行為、定義句、能力敘述與架構層級行為描述，通常維持無標記
- 將至事件如 `about to / soon / nearly / on the verge of`，優先：
  - `快要...了`
  - `就要...了`
- 否定已完成事件時，優先用 `沒 / 沒有`

一般事實或能力敘述不補 `了`：

- 避免：`這個單元讀取了資料並回傳了結果`
- 優先：`這個單元會讀取資料並回傳結果`
- 優先：`這個單元負責讀取資料並回傳結果`

慣常行為、重複工作流與靜態偏好也不補 `了`：

- 避免：`這個服務每天啟動了都會先載入設定`
- 優先：`這個服務每天啟動時都會先載入設定`
- 避免：`這個模組最適合了做快取層`
- 優先：`這個模組最適合做快取層`

已完成、帶結果事件可用動詞後 `了`：

- `The compiler folded the expression into a constant.` -> `編譯器把這個運算式折疊成常值了`
- `The system initialized the buffer.` -> `系統已經初始化 buffer 了`

強調已成立的新情況優先句尾 `了`：

- `This feature is now available.` -> `這個功能現在可以用了`
- `The interface is stable now.` -> `這個介面現在穩定了`

將至事件：

- `The demo is about to start.` -> `展示快要開始了`
- `It is going to rain.` -> `快要下雨了`

被否定的完成事件改用 `沒 / 沒有`：

- 避免：`系統不初始化了這個 buffer`
- 優先：`系統沒有初始化這個 buffer`
- 優先：`系統沒有完成更新`

帶數量詞的完成事件：

- `The service retried three requests.` -> `服務重試了三次請求`
- `We ran five tests.` -> `我們做了五次測試`
- Note：`V + 數量詞 + 名詞 + 了` 常會偏向句尾 `了` 的新情況語感，不等於單純的完成體

例：

- 避免：只因為英文是過去式，就在定義句補 `了`
- 優先：只有在完成體或狀態變更真的重要時才用 `了`

### 2.6 `把 / 被 / 受`

- `把`
  - 只在「處置 + 結果」真的更清楚時使用
  - `把` 後名詞組通常要是定指或殊指
  - 若句子缺乏明確結果、終點或收束，普通主動句通常更自然
- `被`
  - 不可機械式地把英文被動句轉成 `被`
  - 先決定是否真的要把受事者推到前景
  - 若事件是中性敘述，優先考慮主動、無主句或框架先行
  - `被 + 名詞組` 與後面的動作片段通常連在一起判讀，不要把它們當成鬆散零件隨意抽換
- `受 / 受到`
  - 不是一般 `被` 句的修順器
  - 只有在語義真的是承受、遭受或受到影響時才用
  - 優先搭配事件名詞，如 `批評`、`打擊`、`影響`
  - 較完整的補語多半更適合 `受到`，已固定下來的短搭配才偏向 `受`

`把` 字句的基本觸發條件（處置 + 結果）：

- `The compiler folds the constant expression into a literal.` -> `編譯器會把這個常數運算式折疊成常值`
- `The runtime moves the object to the old generation.` -> `執行期系統會把這個物件移到 old generation`
- `clear the bit` -> `把這個位元清掉`
- `split the block into two parts` -> `把這個區塊拆成兩部分`
- `write the data back to memory` -> `把資料寫回記憶體`
- 若只是一般敘述、沒有明顯的處置 + 結果焦點，普通主動句通常更乾淨

`把` 後對象需要定指，結果端也要清楚：

- 避免：`把三個 worker 建立`
- 優先：`建立三個 worker`
- 避免：`把資料處理`
- 優先：`處理資料`

未明說施事者就不要硬補一個做事者：

- 避免：`這份設定被部署腳本覆寫了`（若 source 只說設定在部署過程中被覆寫）
- 優先：`這份設定在部署過程中被覆寫了`
- 優先：`部署過程中，這份設定被覆寫了`

中性事件不要洗成受害式 `被`：

- 避免：`系統被寫出了一個暫存檔`
- 優先：`系統寫出了一個暫存檔`
- 優先：`這個暫存檔會由系統寫出`

真正的受害者視角可保留 `被`：

- `The project got delayed by unexpected dependency issues.` -> `專案又被依賴問題拖延了一輪`
- `His code was overwritten during the merge.` -> `他的程式碼在合併時被覆蓋掉了`

`受 / 受到` 只在承受、遭受或受到影響時才用：

- 避免：`這個欄位受到系統初始化`
- 優先：`系統會初始化這個欄位`
- 優先：`這個欄位會在初始化階段建立`

不要把 `受 / 受到` 當通用被動範本，不要在後面硬接 bare V、結果補語或雙賓語：

- 避免：`這個模組受到系統強制終止`
- 優先：`系統強制終止了這個模組`
- 避免：`使用者受到管理員撤銷全部權限`
- 優先：`管理員撤銷了使用者的全部權限`

合格的 `受 / 受到` 句，通常補語是名詞化事件：

- `be affected by policy changes` -> `受政策變動影響`
- `be subject to criticism` -> `受到批評`
- `undergo punishment` -> `受罰`

### 2.7 代詞、`自己` 與照應

- 若要表達局部、單一、無歧義的反身指涉，優先用：
  - `他自己 / 她自己 / 它自己`
  - 或直接重複名詞
- 同一句或相鄰從句若有多個第三人稱候選先行語，不要把關鍵照應交給單寫 `自己`
- 若局部從句裡出現 `我 / 你`，不要想當然認為單寫 `自己` 仍能自然回指上層第三人稱
- 句內若還有其他參與者、領屬者或另一個 `自己`，也要先確認照應路徑仍然穩定
- 一般代詞 `他 / 她 / 它` 不應承擔本該用反身形式表達的自指

多個第三人稱候選並列時，單寫 `自己` 會變成雙重解讀：

- 避免：`主程式被外掛覆寫了自己的設定檔`
- 優先：`主程式被外掛覆寫了主程式自己的設定檔`
- 優先：`外掛覆寫了主程式的設定檔`

一般代詞不要承擔局部反身功能：

- 避免：`主模組呼叫了它的初始化函式`（若其實要表達主模組自己的初始化函式）
- 優先：`主模組呼叫了自己的初始化函式`
- 避免：`排程器更新了它的佇列`（若其實是排程器自己的佇列）
- 優先：`排程器更新了它自己的佇列`

言說 / 態度動詞下的 `自己` 容易被讀成主語觀點，若不要這種主觀色彩就改寫：

- 避免：`前端團隊認為自己的測試覆蓋率需要提高`（若上下文其實可能是後端團隊的覆蓋率）
- 優先：`前端團隊認為他們的測試覆蓋率需要提高`
- 優先：`前端團隊認為後端團隊的測試覆蓋率需要提高`

### 2.8 連接詞、glue word 與 discourse 骨架

- 若 source 關係在中文直譯後不夠明確，應補入最小必要的簡潔連接詞
- 把 function word 與小型 discourse marker 視為高風險區，不要等到最後才清
- 起草與 reread 時刻意檢查：
  - `的 / 地 / 得`
  - `了`
  - `把 / 被`
  - `就 / 才 / 再 / 還`
  - `因此 / 然而 / 於是 / 此外`
- 常用 glue word：
  - `的`
  - `地`
  - `會`
  - `先`
  - `再`
  - `但`
  - `因此`
  - `同時`
  - `接著`
  - `此外`
  - `在...後`
  - `在...時`
- 必要時補完整的中文成對連接詞：
  - `因為 / 由於 ... 因此 / 所以 ...`
  - `雖然 ... 但 / 仍然 ...`
  - `如果 ... 就 ...`
  - `不但 / 不僅 ... 還 / 也 ...`
- 若相鄰句子本來就自然，不要機械式地補成對

常用引介例子與補充的寫法：

- `such as ...` -> `例如...`，必要時拆句
- `In addition to ...` -> `除了...之外，...也...`

英文隱含的子句關係在中文裡要明示：

- `while A, B` -> `在 A 的同時，B`
- `as a result, ...` -> `因此，...`

小型 function word 校正也要順一次：檢查 `的 / 地 / 得`、`把 / 被`、`就 / 才 / 再 / 還`，以及 `因此 / 然而 / 於是 / 此外`

- `robust detector` -> `穩健的偵測器`
- `systematically compare` -> `系統性地比較`
- `preserved well` -> `保留得很好`

例：

- 避免：只靠英文骨架硬撐，不補任何關係標記
- 避免：`指令取回後會先解碼`，如果 source 其實只是在描述並行或背景事件
- 避免：把連接詞一路疊成一長串

### 2.9 結果表述、補語與長 `的` 鏈

- 若某個操作會產生明顯新狀態，中文可考慮結果補語
- 動詞後位置很擠，看到賓語、結果、頻率、持續時間互相搶位時，優先重排
- 中文可以有 `...的...` 結構，但不要把多層資訊全塞進一條前置 `的` 鏈
- 若名詞前已掛兩層以上修飾，優先：
  - 改寫成子句
  - 把部分資訊移到中心名詞之後
  - 拆句

常見技術動詞的結果補語譯法：

- `clear` -> `清掉`
- `split` -> `拆成...`
- `write back` -> `寫回...`
- `lock` -> `鎖住`
- `open` / `close` -> `打開` / `關閉`

只有在不改變技術語意、且結果狀態真的需要被標出來時，才使用結果補語

`write-back` 類術語的邊界：

- `回寫` 保留給 `write-back` 類快取 / 儲存策略名稱，例如 `write-back cache` 這個固定名詞
- 一般動詞 `write back` 仍優先譯為 `寫回`，不要因為術語看起來像就寫成 `回寫`

例：

- 優先：`把資料寫回記憶體`
- 優先：`write-back cache` -> `回寫快取`
- 避免：把一般動作 `write the data back to memory` 改譯成 `把資料回寫到記憶體`

`V 得 ...` 後不要再硬塞顯性賓語，若只是描寫方式 / 程度，把賓語移出：

- 避免：`整理得文件很清楚`
- 優先：`文件整理得很清楚`
- 避免：`寫得這份報告很完整`
- 優先：`這份報告寫得很完整`

動詞後區域別讓賓語、頻率與持續時間互相搶位：

- `系統連續監控了這個服務三個月` -> `系統連續三個月都在監控這個服務`
- `我維護過兩年舊版部署流程` -> `我做過兩年的舊版部署流程維護工作`

抽象名詞堆疊優先拆成動詞驅動的表述：

- `resource allocation strategy evaluation` -> `評估資源配置策略`
- `mask value determination flow` -> `決定遮罩值的流程`

長 `的` 鏈不要一路塞在同一個名詞前，優先拆成子句或後置：

- 避免：`由控制流重整機制所維護的執行遮罩更新流程`
- 優先：`這個執行遮罩更新流程由控制流重整機制維護`

### 2.10 AI 腔、抽象摘要與 explanation concreteness

- 最重要的一點：避免使用「否定句子 A，而是/其實/真正...等補充句 B」的形式，不要為了避免誤會而寫這種補充，直接將 B 敘述清楚
- 避免把下列句型當成預設修補模板：
  - `被組織成...`
  - `以...為目標來...`
  - `可被...所...`
  - `不是...而是...`
  - `所謂...就是...`
  - `這也意味著...`
  - `一種常見方法`
  - `指令取回後`
  - `文獻中被提出`
- 上述 stock anti-pattern 在兩個位置都要警戒：
  - 首段 opening 的 bare opener，特別是 `不是`、`所謂`、`這也意味著` 這類開頭
  - 文中任意位置的 paired / standalone 形式，如 `不是...而是...` 整組，或 `這也意味著` 自成一句
- explanation-oriented writing 不可只列抽象類別名稱，必須交代具體檔案、具體責任、具體行為
- 若用了 workspace 內部術語，首次出現時要用白話展開
- 欄位名、Mode 名、checklist 名與 workflow 控制詞，只供 agent 在內部判定，不是正式中文的優先用語
- 除非那是來源術語、glossary 既定譯法、檔名 / path / rule id，或使用者明示要保留的名稱，否則不要把這類控制詞直接寫成固定中文名詞
- 長句可以更精確，但長句應補足條件、動作、結果與因果，不要只把內部控制詞串成一串名詞
- 禁止為了簡短敘述，而自行創建不存在的名詞，例如 `名詞化`、`補充化` 等，`化` 一詞嘗試這種情境的關鍵字，不要這樣做，直接將意圖敘述清楚，例如 `名詞化` 應為 `將眾多名詞敘述清楚` 等意義、`補充化` 應為 `將較為細節的事項也說明清楚`

對 repo guide、workspace README、code report、workflow explanation、system overview 與風格檢查摘要這類解說型寫作，額外要求：

- 不可只靠內部分類標籤撐完整段
- 常見需要展開說明、或直接改寫成白話句子的內部術語包括：
  - `參考依據`
  - `規則優先序`
  - `術語邊界`
  - `工作模式`
  - `開工前檢查關卡`
  - `baseline`
  - `前一輪已確認的決定`
  - `這次輸出要交付的內容`
  - `遇到規則衝突時先停下確認`
  - `任務暫存筆記`
  - `寫入前重新檢查這次修改波及的段落`
- 當你在描述某個 layer、folder、file family 或 rule family 時，至少要補出下列其中兩種具體資訊：
  - 裡面放了什麼
  - 它控制什麼實際決策
  - agent 或使用者在什麼時候會讀它
  - 它和相鄰層有何差異
  - 一個代表性檔案或例子
- 優先使用外部讀者看得懂的說法，例如：
  - `原生的中文技術文章`
  - `翻譯文章，內含原文與譯文對照`
  - `開工前檢查表`
  - `句型改寫範例`
- 避免只列抽象分類的摘要，例如 `規則優先序、術語邊界、工作模式、開工前檢查關卡`
- 若正式輸出需要提到這些概念，優先改寫成完整句子，說明誰會在什麼情況下讀哪個檔案、做哪個判斷，或重新檢查哪一段內容
- 若你說某個 folder 裡有 `參考依據`、`rules` 或 `workflow`，下一句必須說明那些詞在實務上指的是什麼

例：

- 避免：`這裡主要處理術語邊界`
- 優先：`這裡主要決定哪些詞保留英文、哪些詞翻成中文，以及章節內第一次出現的詞要不要先做雙語介紹`
- 避免：`這一輪要先做受影響範圍重驗證`
- 優先：`若這一輪會修改既有段落，寫入前先重新檢查這次改動波及的段落`
- 避免：`這段主要在處理 output contract`
- 優先：`這段主要在說明這次最後要交付的是完整譯文、review 報告，還是其他特殊形式的輸出`
- 避免：`先延續既有 continuity`
- 優先：`如果這仍然是在接續同一個任務，就沿用前面已經確定的術語、引用方式與段落風格`

## 3. 標點、空格與語言形式

### 3.1 全形 / 半形標點

- 中文段落預設使用全形標點
- 一般分句停頓使用全形 `，`
- 中文段落中的並列項目使用全形 `、`，除非語境是 literal code、raw data 或明顯需要其他 field list 形式
- 下列情況保留半形：
  - 十進位小數點
  - 檔名分隔符
  - URL、email、path
  - time token，如 `8:00`
  - code、CLI syntax 與其他 raw token
  - 引用的外部標題，這通常會使用書名號或引號包起來
- 不要把拉丁文字相關半形標點直接擴散到一般中文段落

例：

- 優先：`這裡有 3 個欄位，分別是 opcode、mask 與 width`
- 避免：`這裡有 3 個欄位, 分別是 opcode, mask 和 width`

### 3.2 引號、書名號與括號

- 中文段落內的一級引號使用 `「」`
- 引號內的引號使用 `『』`
- 若 source 在正常段落中標示的是書名、手冊、期刊、報紙、戲劇、電影或其他作品標題，優先採中文書名號，例如 `《》`
- 若句末標點屬於引文句子本身，通常留在引號內
- 分號與冒號通常留在引號外
- 若括號內是中文或中英混合補充內容，使用全形 `（）`
- 半形 `( )` 保留給英文段落、function call、raw syntax、Markdown 語法、URL、inline code、inline math 或 code block
- 中文引號與全形括號內外不留半形空格

例：

- 優先：`這種作法稱為「延遲繫結」`
- 優先：`最低一個 bit（lowest-order bit of the first byte）`
- 避免：`這種作法稱為 "延遲繫結" `

### 3.3 中英 / 中數空格

- 中文與獨立拉丁字詞之間，一般保留一個半形空格
- 中文與獨立阿拉伯數字之間，一般也保留一個半形空格
- 序數、量詞與日期同樣依這個原則處理，例如：
  - `第 10 篇`
  - `3 個項目`
  - `2024 年`
- 不可拆開固定閉合形式，例如：
  - file path
  - URL
  - email
  - code identifier
  - inline code
  - `16GB`
  - `8:00`
  - `10%`
  - `p5-p10`
- Markdown link 前後是否留空格，看 `[]` 內的可見文字，不看 URL

單位與同檔 spacing 自洽：

- 對 `m`、`kg`、`ml` 這類單位，依文件類型與讀者決定保留符號或改寫成中文單位
- 同一份檔案內的 spacing style 必須自洽，不可一部分保留半形空格一部分又緊貼

例：

- 避免：`在CUDA環境中共有3個stage`
- 優先：`在 CUDA 環境中共有 3 個 stage`
- 優先：`請參考 [CUDA Guide](...) 的說明`
- 優先：`請參考[附錄](#appendix)中的定義`

### 3.4 句末標點、段末句號與句界空格

- 預設 Markdown 段落中傾向於省略段末全形句號
- 若目前檔案已建立穩定 house style，或 task 明確要求保留段末句號，則沿用既有風格
- Markdown 段落的句末不可用 `，`、`、`、`；` 等延續標點收尾
- 閉引號、閉書名號或閉括號只是外層包覆，仍要檢查內部最後一個可見標點
- `：` 只在後面真的要引出清單、code block 或補充說明時保留
- 若同一 Markdown 行內以 `。`、`？`、`；` 接續下一個段落，標點後保留一個半形空格
- 若標點後有閉括號，空格放在閉括號之後
- 若標點後接中文閉引號，中文引號外側不加半形空格
- 若括號內容本身是一個完整獨立句，其句末標點留在括號內

例：

- 避免：`這一步先建立索引，`
- 優先：`這一步先建立索引。 接著再處理查詢路徑`
- 優先：`作者稱這是必要條件。`（若該檔案採句號風格）

### 3.5 破折號、分號、冒號與列點引介

- 不使用破折號作為段落的插入或中斷標記，包含 `──`、`—`、`–`
- 需要插入、補充或中斷時，優先改用：
  - 逗號
  - 冒號
  - 括號
  - 拆句
  - 重寫
- 正式輸出預設不用分號
- 一般承接、因果、轉折、補充或順序關係，一律優先拆句、改逗號、改冒號、改成 bullet，或重寫句子
- 只有在同一說明目的下平行列舉多個對象，而且改成句號或 bullet 會明顯降低可讀性時，才可保留分號
- 若只是想把兩個完整子句接在同一句裡，不可使用分號
- 中文列點引介使用全形 `：`
- 一般段落若以全形 `：` 引出後續清單，冒號後與清單之間保留一個空行
- 若 `：` 位於某個 bullet / numbered item 內，且後面接的是該項目的巢狀清單，則不額外插入空行

例：

- 避免：`系統分成三層 -- 前端、排程器、後端`
- 優先：`系統分成三層：前端、排程器、後端`

分號視為例外標點，不是一般 prose 的連接符號。 這種例外極少發生。 即使遇到平行列舉，也通常先改寫成句號或 bullet：

- 例如可改寫成三點：
  - `increment` 和 `decrement` 這對名稱描述的是操作本身，也就是把值加一或減一
  - `signal` 和 `wait` 描述的是它們常被拿來做什麼
  - `V` 與 `P` 則是 Dijkstra 當年提出的原始名稱

### 3.6 數字、日期、時間與貨幣

- 測量值、統計數字與公曆日期通常使用阿拉伯數字
- 若英文原文把數字拼成文字，而中文用中文數詞讀起來更自然，也可改用中文數詞
- 對財務、統計或其他大數字情境，若千分位分隔符能提高可讀性，就應保留
- 日期通常採中文順序，如 `YYYY 年 MM 月 DD 日`
- 時間可依 source 格式保留，或在中文格式更清楚時改寫成中文格式
- 貨幣可視句子需要，採符號在前或中文單位在後的寫法

### 3.7 語域與語氣

- 正式輸出一律使用繁體中文與面向臺灣的用語
- 不可引入簡體中文寫法或中國大陸用語
- 盡量貼近原文的語域
- 若 source 明顯正式，譯文也應維持正式
- 若 source 明顯較口語，譯文可自然，但不可滑進原文沒有授權的俚語感
- 未翻譯的英文應維持半形拉丁字
- 若英文原文在中文段落中帶有簡單複數 `s` 的 acronym，若譯文用單數更自然，可考慮正規化為單數
- 在預設 Markdown 輸出中，避免使用粗體與斜體，需要強調時改用「」

## 4. Markdown、Citation 與結構呈現

### 4.1 段落、換行、Bullet 與 list

段落長度預設：

- 每段優先控制在 2-5 行
- 高密度的段落通常應低於約 150 個中文字
- 短段落政策不等於 sentence-per-line 的硬斷行
- 正式輸出以乾淨 Markdown 為主
- 不要求段落和 source 1:1 對應
- 只要資訊忠實，必要時可重分段
- 一般段落若只是同一語境內的連續句子，不要只因句子結束就另起一行
- 若內容需要另起一行，必須以空行明確分段，不可留下沒有空行的句間硬斷行
- 一般段落行內不應殘留連續兩個半形空白
- 對多個平行短項目，例如 loops、blocks、fields、units，使用 bullet
- 若每個項目較長，可用階層式 bullet
- 相鄰 list item 之間預設不插入空行
- 同一個 list item 若直接接巢狀清單，也不插入空行
- 一般 top-level code block 前後各保留一個空行
- 若 code block 位於 bullet / numbered item 內，前後空行可依上下文省略
- Markdown custom container / directive fence 也比照 code block 處理
  - 三個以上 `:` 形成的 fence（例如 `:::info`、`:::tip`，label 不限於這些）
  - opener 獨立成行，標準形式為 `:::label`
  - closer 獨立成行，標準形式為 `:::`
  - top-level container 外側保留空行
  - 內容不可黏在 opener / closer 上
  - opener 後、closer 前不額外插入空白行
- 非空 Markdown 檔案必須以 EOF newline 結尾

常見的列表引介與步驟化改寫：

- `The following ...` -> `以下...`，後接列表
- 規格步驟敘述優先保留編號、縮短句尾、把動詞往前提
- `A, B, and C` 類並列，中文用頓號或改成 bullet，最後一項前優先 `與`
- 段落內包多層邏輯時主動重分段，而不是用分號硬串

### 4.2 Markdown / LaTeX / HTML / CSS 邊界

- 若 source 使用 LaTeX / TeX 公式，譯文對應段落也應保留公式
- 不可把公式攤平成普通文字
- 預設保持 inline math 為 inline、display math 為 display
- 翻譯公式周圍的段落，不翻公式 token 本身
- 起草前先正規化 source noise，例如：
  - sentence-per-line artifact
  - 斷裂 hard wrap
  - copy/paste 縮排噪音
  - layout-only wrapper tag
- 若 source-side HTML 只是呈現層包裝，且可直接映射成 Markdown 結構，就應轉成 Markdown
- 忽略 source-side custom CSS、inline style attribute 與其他純呈現層 wrapper
- 除非 source 結構本身有問題，否則保留 heading、list、table、code fence 與 inline code marker
- 在中文段落中，若不是 literal code 或 raw field list，最後一項前優先使用 `與`
- 程式碼字面與說明段落混用時，程式碼字面不動，敘述改成自然中文

例：

- 避免：把原本的 display equation 攤平成一段普通文字
- 避免：`$a \equiv b \pmod m \quad\text{ 且 }\quad c \equiv d \pmod m$`
- 優先：`$a \equiv b \pmod m \quad\text{ and }\quad c \equiv d \pmod m$`
- 避免：把 `<style>` block 或 `style=...` 一起搬進正式輸出
- 優先：把 heading wrapper 轉成 Markdown heading

### 4.3 Formal citation 與 ordinary hyperlink

- 先判斷 source scope：
  - formal citation apparatus present
  - ordinary hyperlinks only
  - no citation / no link
- 只有在 source 本來就有 formal references，或使用者明確要求 formal references 時，才建立 formal citation apparatus
- 不可只因為存在 ordinary hyperlink，就自行發明 academic citation apparatus
- citation 形式依局部區塊決定，不必把整份檔案硬寫死成單一形式
- 同一份檔案中可以同時出現 formal citation 與 ordinary hyperlink，但每個局部區塊都要自洽
- formal citation apparatus 的基本形式：
  - 文中標記：`<sup>[[L09]](#7)</sup>`
  - 同位多引：`<sup>[[L09]](#7), [[S09]](#14)</sup>`
  - 文末章節：`## 引用文獻` 或 `## References`
  - 條目形式：`- <a id="7">[L09]</a> ...`
- `[[...]]` 內的顯示 label 可直接沿用 source key，例如 `2`、`L09`、`KE+62`
- `(#...)` 的 target 與文末 `<a id="...">` 對應即可，不必強迫顯示 label 與 anchor id 長得一樣
- 整理 formal references 時，以 source 的引用清單與引用位置為準。 不要只因 target 內目前看起來沒有 superscript 就直接刪除某條 reference，也不要反過來自行補出 source 沒有的 formal citation
- formal `References` block 內的 bibliography 主行可保留英文引用慣例，不必硬套中文 prose 標點規則
- bibliography 主行若保留英文篇名引號，使用 ASCII `"`。 若保留英文 apostrophe，使用 ASCII `'`
- bibliography 主行的人名 initials 依英文整理格式保留空格，例如：
  - `Edward L. Glaser`
  - `D. B. G. Edwards`
  - `M. J. Lanigan`
  - `F. H. Sumner`
- bibliography 主行中的英文縮寫若後面直接接數字或一般 bibliographic 成分，保留半形空格，例如：
  - `Vol. 15`
  - `No. 3`
  - `p. 12`
  - `pp. 45–52`
- 年份簡寫如 `'95`、`'02` 前應保留一個半形空格，例如 `USENIX ATC '95`
- 所有格 `'s` 必須直接接在前一個字後，不可寫成 `Developer 's`
- 若 formal reference entry 含 URL，URL 單獨一個子列點，而且該行只放 URL 本身，不加 `網址：`、`Available at:` 或其他說明文字
- formal reference entry 的中文解釋另開一個子列點，並視同正文中文段落，套用同一套中文用詞、句法、標點與 spacing 規則
  - 若需要逗號、冒號或分號，使用對應的全形中文標點，不要使用半形 `,` `:` `;`
  - 中文說明子列點一般不以半形 `.` 收尾
- `References` 內的中文解釋，優先回答「這篇東西在講什麼」或「作者在這裡為什麼提它」
- `References` 內的中文解釋不要寫成心得文、廣告文案或對讀者下指令的口吻
- 若 source 只給一句平實評論，中文也維持一句平實評論。 不要額外補出更強的稱讚、確定語氣、笑點或讀者命令
- `References` 內的中文解釋原則上不用分號。 若有兩個重點，優先拆成兩句，必要時拆成兩個子列點
- ordinary hyperlink 優先自然的 inline link，例如 `[P0767R1](...)`

例：

- 避免：source 只有 `[P0767R1](...)`，卻額外捏出 superscript citation 編號
- 優先：source 只有一般連結時，保留 inline link
- formal reference entry 範例：

```md
- <a id="8">[I09]</a> "Intel 64 and IA-32 Architectures Software Developer's Manuals" by Intel, 2009.
  - http://www.intel.com/products/processor/manuals
  - 特別注意其中的「Volume 3A: System Programming Guide Part 1」和「Volume 3B: System Programming Guide Part 2」
```

### 4.4 link label、括號與可見文字邊界

- Markdown link 前後空格依 `[]` 內的可見文字判斷，不依 URL 判斷
- 若 label 邊界和外側文字是中文連中文，不留空格
- 若 label 邊界和外側文字是中文與英文 / 數字相接，才保留一個半形空格
- link label 的可見文字應符合正文語氣，不要把 URL query、追蹤參數或噪音一起暴露出來
- Markdown link URL 不保留外部來源或廣告追蹤 query，例如：
  - `fbclid`
  - `utm_source`
  - `utm_*`
  - `gclid`
  - `msclkid`
- 清理 tracking query 時，只移除追蹤參數，保留原始 path、必要 query 與 fragment

例：

- 避免：`詳見 [附錄](#appendix) 中的說明`
- 優先：`詳見[附錄](#appendix)中的說明`
- 避免：`詳見 [CUDA Guide](...)第 3 節`
- 優先：`詳見 [CUDA Guide](...) 第 3 節`

## 5. 正式輸出一致性

### 5.1 正式輸出檔只能包含的項目

- 最終譯文 / 正式正文
- 必要的 citation apparatus
- 屬於最終正文的一般 hyperlink

### 5.2 正式輸出檔不得包含的項目

- 原文區塊
- 開工前檢查摘要
- 自檢區塊
- 對話痕跡
- 除錯筆記
- 更新後文件不應該有舊文件的殘留
- 本應忽略的 source-side custom CSS 或呈現層 style block
- 本應正規化成 Markdown 的 raw presentational HTML wrapper
- 應放在 `context_memory.md` 的 task-local memory note

例：

- 避免：`不像先前的版本，我們現在 a 取為 2`
- 優先：`在 a 取為 2 的情況下`
